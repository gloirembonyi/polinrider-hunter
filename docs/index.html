The malware that
kept coming back.

PolinRider hides a loader in one line of a build config, behind five hundred characters of whitespace. It resolves its command server from the Ethereum blockchain and leaves a hidden interpreter running long after the build ends. This sweeps your whole computer for it - not one project, every file under your home directory, and every drive if you ask - removes what it finds, and keeps watching. It repairs the branches on GitHub the attacker re-pushed, down to the poisoned commits in their history, and ships an AI agent you can simply ask to do the rest - or plugs into the agent you already use, as an MCP server, with no key of ours.

Install

One command. Then it looks after itself.

The installer puts a single binary in a user directory - no administrator or root - sweeps the whole machine and cleans what it finds, then registers a background guard that runs at every login.

Downloads a prebuilt binary (under 1 MB) - nothing to compile. Installs to %LOCALAPPDATA%\Programs\polinrider-hunter and adds it to your user PATH. No administrator rights needed. 

# Terminal - needs a Rust toolchain (see note)

No signed macOS binary is published yet, so the installer builds from source - about a minute. It needs cargo; if that is missing it tells you exactly what to run rather than failing quietly: curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh. Installs to ~/.local/bin.

The threat

What PolinRider actually does

Worth understanding, because it explains every design decision underneath.

01 - HIDING

It lives in a build config

The payload is appended to one line of a file like postcss.config.mjs, tailwind.config.js or eslint.config.mjs, behind roughly 500 characters of spaces or tabs. In an editor the code sits far off the right edge; in a diff the line looks untouched.

It runs on any dev, build or lint that loads the config - and inside your editor too, because extensions like ESLint and Tailwind IntelliSense execute the project config in their own Node process.

02 - COMMAND & CONTROL

Its C2 lives on a blockchain

Rather than a domain that can be taken down, stage 1 reads the most recent transaction from a hardcoded Ethereum sender through public RPC endpoints, then decodes two IPv4 addresses out of the transaction's to field - bytes 0–3 and 4–7.

The operator moves the C2 by sending a cheap transaction. Nothing to seize, nothing to blocklist. The technique is known as EtherHiding.

03 - DELIVERY

Cleartext on port 443

Stage 2 arrives over plain HTTP on port 443, which looks like TLS to anything merely counting ports. The request wears a spoofed Chrome User-Agent and carries a campaign id in a Sec-V header.

The response can deliver the payload in an X-Payload-B64 header, so a HEAD request leaves no body to inspect. It is XOR-encrypted with a key baked into stage 1.

04 - PERSISTENCE

It runs twice, once invisibly

In-process via eval, and again as a detached child: 

spawn("node", ["-e", env + code], {
  detached: true,
  stdio: "ignore",
  windowsHide: true
}).unref()

A hidden interpreter with no console and no parent, which outlives the build that started it. require and module are handed across through globals, so stage 2 has the full run of Node.

05 - PROPAGATION

It re-pushes your own commits

With a stolen GitHub credential it rewrites your latest commit - same message, same author date, different hash - with the payload, a config.bat or branch_structure.json, and .gitignore lines that hide them. Then it force-pushes that twin to every branch of every repository the token can reach.

Your editor shows it as "1 outgoing, 2 incoming" on every project. A cleanup commit on top makes the tip clean - and leaves the poisoned twin in history, the commit everyone still pulls.

06 - EXECUTION ON OPEN

Opening the folder runs it

The autorun variant ships a .vscode task with "runOn": "folderOpen" and switches task.allowAutomaticTasks on, so the moment a fresh clone is opened in VS Code or Cursor, node runs a script saved as a font - public/fonts/fa-solid-300.llf.

No build, no install, no prompt. That is how the machine this tool was written on was re-infected in October 2026: clone, open, compromised in three seconds.

This is not hypothetical. A live stage 2 was found running on the machine this tool was written on - parented by the code editor, C2 already resolved, hours after every repository had been cleaned. Removing a file stops the next build. It does nothing about the process already running.

The gap

Why it kept coming back

On the machine this was first pulled from, three scanners were already in place: a pre-commit hook, a CI job and a check in the Docker build. All three matched global\.i=. The live variant writes it with spaces.

caught
global.i='A8-2941';…
missed for months
global.i = 'A8-2941';…
as it appears
};····························································global.i = 'A8-2941';…

One character of whitespace walked it past every gate, while each of them reported clean. Re-scanning with a corrected pattern found it on most branches of every repository on that machine. Windows Defender missed this variant too.

So this tool does not rely on a list of strings alone.

Detection

Three layers, deliberately independent

LAYER 1

Signatures

Known strings: the dead-drop sender address, /0x/cls, X-Payload-B64, global['!'], _$_1e42, AUTH_API_KEY, campaign tags.

Fast and precise - but only for variants already seen.

LAYER 2

Structure

A run of 200 or more spaces or tabs followed by code. Variant‑agnostic: a new build can change every string it contains, but not this.

The padding is the camouflage. Dropping it means showing up in the editor.

LAYER 3

Process

Any running node -e whose command line carries the stage‑2 globals - global['_V'], global['_t_s'] and friends.

Finds an infection whose file you already cleaned, or that arrived another way.

Severity is not decoration

Critical means unambiguous, and is safe to remove automatically. Suspicious means consistent with PolinRider but plausible in honest code - Ethereum RPC hostnames, windowsHide - and is only ever reported.

Padding alone counts as critical only inside a file PolinRider is known to target. In a README it is a markdown table, so it is dropped there entirely.

One shape needs no such caution: a file that is nothing but a line of 200 or more tabs or spaces followed by a kilobyte or more of code - the api.js dropper - is critical whatever it is called and whether or not a known string matches. No honest source file begins with 200 blank columns. A package.json script that runs such a file (node api.js && … on every dev or build) is flagged with it, as script-runs-dropper.

It does not flag the detectors

Every malware scanner contains the strings it hunts for. Any file carrying the token POLINRIDER-HUNTER-DETECTOR is skipped wherever it lives, so a project opts its own gate out explicitly and the exemption travels with the file.

CI gates are also recognised by content - signatures sitting inside a grep pattern, next to the grep itself.

The marker is public, so it cannot excuse a padded dropper or a script that runs one. A scanner quotes indicator strings; it does not begin with a 200-column pad and kilobytes of code.

Where this list comes from. Partly from samples pulled off an infected machine, and partly from the public dossier on the campaign - it is attributed to a DPRK-linked actor and has put 108 malicious packages across npm, Packagist, Go and the Chrome Web Store, with two obfuscator variants live at once. Local samples caught the newer Ethereum dead drop; the published research supplied the TRON and Aptos ones, the propagation script and the trojanized package names.

Two deliberate refusals. A byte-level cut is the right tool for an appended payload and the wrong tool for structured or wide-character text. In .vscode/tasks.json the indicator sits inside a task's "command" value, and cutting to end of line would leave a dangling "command": " and an unparseable file. For UTF-16, the match offsets belong to the decoded text, not to the file's bytes. Both cases name the problem instead of guessing - and there are tests holding each line.

Removal

Surgical, and always reversible

Quarantine before writing

Every original is copied aside and indexed before anything is modified, so a wrong cut is always recoverable. polinrider-hunter quarantine lists them with the indicators that triggered each one.

Never rewrite bytes we did not mean to

Read the file to lines, edit, write the lines back - and you have silently rewritten every line ending in it. On a CRLF repository that turns a one-line security fix into a whole-file diff and buries the actual change in noise.

So the healer splices the byte buffer and leaves every other byte untouched.

The cut starts at the beginning of the whitespace pad, so the camouflage goes with the payload. Cutting repeats until the file is genuinely clean - a config visited twice carries one pad and payload per visit, and stopping after the first would leave the rest in place.

Verified against the real thing. Healing the live payload out of an infected postcss.config.mjs produces a file byte-identical to a hand-reviewed fix - and 96 bytes smaller, because the injected createRequire scaffolding goes too, leaving the genuinely pristine original.

Your repositories

Clean branches, clean history

Your working tree can be spotless while every branch on GitHub carries the payload. git status shows nothing and git pull would bring it all back. So the audit reads the branches themselves, and the default repair is one ordinary commit on top - safe on a branch your whole team pushes to. When you want the poisoned commit gone from history as well, that is there too.

Nothing is rewritten and nothing is forced. One new commit removes every infected file - the padded config line, api.js, the node api.js && hook in package.json, the folder-open task, the fake font, config.bat, branch_structure.json, temp_*push.bat and the .gitignore lines hiding them - and is pushed as a plain fast-forward. The teammate's clone still fast-forwards. If anyone pushed in the meantime, the push is refused, not forced. The poisoned commit stays in history until the owner purges it (--history prints the command), but nothing that pulls the branch will run it.

AUDIT

Every branch, nothing checked out

repos fetches and audits every local and remote-tracking branch straight out of the object database - no pull, no checkout, nothing written to your working tree. Content, file names, armed .vscode autoruns and fonts that are really scripts, plus each repository's git config and hooks. Give it a URL instead of a path and it audits through a bare clone in a temporary directory. Every git command it runs has core.fsmonitor, hooks and the pager switched off, so auditing a hostile repository cannot execute that repository's config.

--REPAIR

One forward commit, no force

The default. Builds a clean commit on top of each infected remote branch inside git's object database - the infected tree is never checked out, so no payload ever lands on disk - and pushes it as an ordinary fast-forward. Refused if someone pushed meanwhile. Teammates' work on top of the infection is not a problem, which is what makes it right for shared branches. POLINRIDER_SKIP_REMOTES=upstream,fork keeps it off remotes that are somebody else's.

--FIX

Your clean branch, pushed back

When a clean local branch tracks the poisoned one, --fix pushes it with --force-with-lease pinned to the exact commit it audited - and only when every extra commit on the remote is the infection. Anything that looks like real work gets BLOCKED, with the file names. A rewrite: for branches only you push to.

--EXCISE

The poisoned commit, cut out

No local copy needed. It finds the commit that brought the payload in, rebuilds it with every infected file restored from its parent, under the original message, author and dates, and folds cleanup commits away. It refuses when real work landed after the infection, and never pushes a commit that still audits infected.

--HISTORY

Older copies, still in the object database

A clean tip is not a clean repository. --history walks every blob reachable from any ref, names the commits holding each payload, and prints the git filter-repo command that purges them for good.

It first looks for your exact original in your local clones - same message, same date, identical clean files - and rebuilds only when there is none.

A twin of your commit means your credential pushed it. Repairing the branches is half the job: rotate your GitHub tokens and SSH keys, revoke sessions and OAuth apps, and rotate every secret that sat in a .env on disk. A branch reported with can_write: false is one your account cannot push to - the tool names the owner and who pushed the infected commits instead of routing around it.

Repos you cannot fix

Half the infected branches on a real account belong to someone else - an organisation, a client, a fork you contributed to. The audit still reads them; the repair tells you who can.

WHAT IT SHOWS

Owner, pusher, access

For every infected branch: the repository's owner, who pushed the infected commits (in the campaign that is the victim whose credential was stolen - usually not the attacker's own account), and can_write - whether the credentials on this machine can push there. false means ask; the tool will not try another route.

WHAT TO TELL THEM

One command, or one pull request

Send the owner or the pusher this page and one line: run polinrider-hunter repos --repair on your clone. It adds one normal commit, no force push, and nothing infected is checked out. If they would rather not run anything, open a pull request with the same change and ask them to merge it - the repair is an ordinary commit, so it reviews like one.

WHAT STAYS

History is the owner's

A forward commit makes the branch safe to pull. The poisoned commit is still in the repository's history - reachable by hash, in every clone, and kept by GitHub until the owner purges it with the git filter-repo command --history prints, and asks GitHub support to collect the unreachable objects. Say so when you hand it over; it is their call.

How it works

The model never touches your machine. It proposes; the binary decides and acts.

1 - YOU ASK

A message, a method, a toolbox

You type what you want. The agent sends the model a fixed system prompt - its method for incidents is triage, scope, contain, eradicate, root cause, recover, report - a description of its thirty-odd tools, your message and the conversation so far.

2 - THE MODEL PROPOSES

One tool call at a time

The model answers with a proposed tool call - scan these paths, run_command this, edit_file that - with every argument spelled out. That is all a model can do here: ask.

3 - THE HUNTER DECIDES, THEN RUNS IT

The gate, then the work

The binary classifies the call against your permission mode: a reader runs at once, a change is shown to you first, a short list is refused in every mode. Then the binary itself runs the tool - the same code hunt and repos use - and captures the result.

4 - AND AROUND AGAIN

Until it says finish

The result goes back to the model - capped at 16 KB and marked as untrusted data - and the loop repeats until the model calls finish with a summary, asks you a question with ask_user, or reaches 60 steps in one turn and pauses (continue resumes). Ctrl-C stops the current step; twice quits.

DOES THE WORK

A terminal, not a chatbot

It runs commands in cmd, PowerShell or sh, reads, writes and edits files, searches with glob and grep, keeps a visible plan for longer jobs, and verifies after every change - the build, the tests, a re-scan.

ANY PROVIDER

Bring your own key

Claude, OpenAI, Gemini (free tier), OpenRouter, Groq, DeepSeek, Ollama on your own machine, or any OpenAI-compatible endpoint. Switch mid-conversation with /provider or /model; the conversation comes along.

YOU DECIDE

Four permission modes

read-only investigates and reports. ask, the default, shows every change first. workspace-write edits files in your project freely and asks for the rest. full-access asks for nothing.

"Read-only" is decided per command, not per name: every segment of a pipeline must be a known reader in a reading form. A single &, $(…), backticks, a real redirect, sudo, npx, git -c or a quoted powershell -Command / cmd /c body that is not itself read-only all ask. Commands it runs on its own get core.fsmonitor, hooks and the pager switched off, so git status in a poisoned repository cannot run the attacker's code. Reads of secret stores - .env, .ssh, .git-credentials, gh hosts, .npmrc, the hunter's own config - ask every time and are refused in read-only. web_fetch goes straight to a built-in list of research sites (GitHub, NVD, OSV, npm, PyPI, VirusTotal, Socket, MS Learn, MDN, Stack Overflow, Wikipedia, docs.rs, crates.io); any other host asks, and private, loopback and link-local addresses are never fetched, redirects included. Keys never appear on curl's command line. Long sessions are compacted to a per-provider context budget, keeping the last exchanges verbatim.

The transcript

Every turn, tool call and result is appended to agent\<timestamp>.jsonl in the state directory - %LOCALAPPDATA%\polinrider-hunter on Windows, ~/.local/share/polinrider-hunter elsewhere - and reports it writes go to reports\ beside it. polinrider-hunter status prints the directory. Read it afterwards, or hand it to someone who has to sign off on what was done.

Keys live in that directory's config.txt, written owner-only, and are only ever printed masked. Environment variables (ANTHROPIC_API_KEY, OPENAI_API_KEY, …) take precedence.

polinrider-hunter mcp turns the binary into an MCP server - the Model Context Protocol that coding agents use to call tools - over stdio. The agent you already use gets the hunter's scanners, audits and repairs as tools, and you never give this tool an API key of any kind: the model is theirs, the hands are ours. It opens no port and talks only to the host that started it.

TWO CALLS TO CHANGE ANYTHING

Dry run by default

clean, hunt, repos_repair - and the kill and remove options of processes and persistence - plan on the first call and write nothing. Only a second call with confirm: true performs it. The host agent has to put the plan in front of you in between - the protocol leaves it no other way to get the work done.

PATHS OR URLS

Not cloned? Still audited

repos_audit and repos_repair take a local clone or a repository URL. A URL goes through a bare clone in a temporary directory: no working tree, nothing checked out, no payload on disk.

IT NAMES WHOM TO ASK

Owner, pusher, can_write

Every infected branch comes back with whether your account can push to it, the repository's owner and who pushed the infected commits. When you cannot fix a branch, the agent can tell you exactly who can - rather than trying harder.

The guard

Runs in the background. Costs nothing.

Three cadences, because the cheap check is the one worth running often.

EVERY 30 SECONDS

Quick

stats a precomputed list of concrete target paths and reads a file only when its mtime has actually moved. No directory walking at all - an earlier version re-walked every repository twice a minute, which is thousands of directory reads to discover nothing had changed.

EVERY 15 MINUTES

Full

Walks the watched trees properly, in case a variant picks a filename not on the list, and rebuilds the quick pass's watch list. Also checks for hidden stage-2 processes.

EVERY HOUR

Git refs

Fetches and audits every branch, local and remote-tracking, reporting anything that arrived upstream. git grep reads straight out of the object database - no pull, no checkout, nothing written to your working tree.

Measured, guarding seven repositories

0.005s CPU per quick pass
4.7MB Resident memory
<1MB Binary on disk
Belownormal Process priority

What it will not do. The guard heals working trees. It never rewrites git history and it never pushes - an automated process that force-pushes to shared branches is a worse problem than the one it is solving. It reports what it finds on a branch and leaves the decision to you: a branch is only repaired when you run repos --repair (one forward commit, no force) or approve the agent - yours or an MCP host's - doing it, and history is only rewritten when you choose repos --fix or repos --excise.

Autostart is a text file you can read and delete

PlatformMechanism

status prints the exact path. A security tool that installs itself somewhere you cannot find is behaving like the thing it removes.

Staying informed

It tells you. You can watch it. You can remove it.

A guard that finds malware at two in the morning and only writes it to a log file has not really told anybody.

NOTIFICATIONS

You hear about it

A desktop notification when something is cleaned, and a louder one when something is found that will not be touched automatically. Tray balloon on Windows, osascript on macOS, notify-send on Linux - all already on those systems, nothing to install.

Check they reach you: polinrider-hunter test-notify. Silence is deliberate on a headless box or locked session - the log still has everything.

MONITORING

You can watch it

monitor is part of the binary: guard health, every watched path, a timeline of detections with the indicators that fired, and the quarantine. Add --web and it prints a link you open in a browser.

Nothing to clone, nothing to install, no Python. Strictly read-only — it never edits config, heals anything or stops the guard. The web view binds to 127.0.0.1 only: it shows where infections were found on your disk, so it stays on your machine.

REMOVAL

You can get rid of it

uninstall stops the guard and removes the hooks, reversibly, and prints exactly what it removed. uninstall --purge also deletes the state directory, the PATH entry and the binary itself.

--purge warns first if the quarantine is not empty - those are the only copies of what was cut out of your files.

The dashboard

# live terminal view
polinrider-hunter monitor

# or a browser dashboard on localhost
polinrider-hunter monitor --web

Works from any directory on any machine that ran the install command. --once prints one snapshot and exits, --json gives the same data for scripting, and log --follow tails the raw events.

Complete removal

# stop guarding, keep everything else
polinrider-hunter uninstall

# leave nothing behind at all
polinrider-hunter uninstall --purge

A running binary cannot delete itself on Windows, so a detached helper waits for it to exit and removes it.

Reference

Commands

Every command below is typed with the program name in front of it, from any directory, in any terminal: polinrider-hunter status, not status. Open a new terminal after installing so it is on your PATH.

CommandWhat it does
polinrider-hunter huntSweep this whole machine: stop any running loader, find every infected file under your home directory, clean it. No setup needed. --drives covers every drive.
polinrider-hunter install [paths…]Watch these directories, install a pre-commit hook in each repo, sweep them now, and start a guard at every login.
polinrider-hunter statusWhere everything lives, and whether the guard is alive.
polinrider-hunter scan [paths…]Report only; change nothing. Exit 1 if anything critical.
polinrider-hunter clean [paths…]Scan, then remove payloads. --dry-run to preview.
polinrider-hunter repos [paths or URLs…]Fetch and audit every branch, local and remote-tracking, without pulling or checking out - plus each repository's git config and hooks. A URL is audited through a bare clone in a temporary directory.
polinrider-hunter repos --repairClean each infected remote branch with one ordinary commit on top of its current tip, built in the object database and pushed as a fast-forward - never forced, refused if someone pushed meanwhile. polinrider-hunter repos --fixPush your clean local branch over a poisoned remote one, with a lease. A rewrite, for branches only you push to. --dry-run shows the push.
polinrider-hunter repos --exciseCut the poisoned commit out of each remote branch and restore your original - no local copy needed. --dry-run shows the plan.
polinrider-hunter repos --historyAudit every blob in history, not just the tips, and print the purge command.
polinrider-hunter agent [paths…]Chat with the AI agent. --task "…" for one job, --investigate for the full investigation, --mode for permissions, --provider/--model to choose.
polinrider-hunter aiWhich providers are set up and which is active. ai setup guides you; ai key <provider> asks for the key rather than taking it as an argument; ai use, ai mode, ai test, ai remove manage it.
polinrider-hunter mcpServe the hunter's tools to another AI agent over MCP on stdio - Claude Code, Cursor, Codex, Windsurf. No key of ours; destructive tools dry-run first and need confirm: true.
polinrider-hunter reportA written incident report: read-only AI investigation with a provider, a factual status report without one.
polinrider-hunter logWhat the guard has been doing. --follow watches live, --all shows everything.
polinrider-hunter procsList hidden stage-2 processes. --kill stops them.
polinrider-hunter persistenceCheck shell profiles, cron and login agents for a way back in. Reports only.
polinrider-hunter protect / polinrider-hunter unprotectInstall or remove just the pre-commit hook.
polinrider-hunter quarantineList the originals kept aside during healing.

Audit a branch before it lands

polinrider-hunter repos ~/work/some-repo

When what you are looking for is malware, you want to know what is on a branch before it reaches your disk in a form something might execute.

Evidence

How it was tested

  • 218 automated tests - 152 unit, 66 end-to-end. The end-to-end suite plants each real attack shape on disk and asserts the payload is gone, the surrounding code is byte-for-byte unchanged, a second pass finds nothing, and the quarantined original still matches. Poisoned remotes are built from real git repositories, and the agent is driven by a scripted model.
  • Against the real payload pulled from git history: all five critical indicators detected, 7,687 bytes removed, second pass silent, result byte-identical to a hand-reviewed fix.
  • A live guard test - a reinfected config with two payloads and mixed space/tab padding, planted in a watched repository. Caught all six indicators and healed both in one 30-second cycle.
  • Six planted infections across five project trees - all four config shapes, the dropped .env, and the payload wearing a .woff2 extension. All removed in 542 ms; three deliberately-clean bystanders untouched.
  • Against a real account - on 11 October 2026 the excise repair rebuilt 152 branches across 114 repositories whose every branch had been re-pushed with a twin. A full re-scan of every branch afterwards: all clean, no twin left in any history.
  • The tests found defects in the tool itself - incomplete cleaning of reinfected files, JSON corruption in tasks.json, and an unbounded search that could swallow unrelated code. All fixed, all with tests.

Payloads in the test suite are inert - the recognisable shape of PolinRider with a harmless body - so running the tests never puts working malware on disk.

Questions

Honest answers

Does it work on Windows, macOS and Linux?
Yes - one codebase, Rust standard library only, no platform-specific dependencies. Windows currently gets a prebuilt binary; macOS and Linux build from source in about a minute, which needs a Rust toolchain. That is a packaging gap, not a portability one.
Why no dependencies at all?
Because the entire subject of this program is supply-chain compromise. Anything it would have pulled a crate for - regex, file watching, JSON - is a small purpose-built module instead. It also means the build needs no network access, and there is nothing in it you cannot read.
Will it slow my machine down?
The guard uses 0.005 s of CPU per 30-second pass and 4.7 MB of memory, at below-normal priority. A full hunt is the heavy part: it reads every candidate file under your home directory, which on a developer machine with editors, browsers and installed applications means tens of thousands of files and ten to twenty minutes. It is mostly waiting on the disk, it runs at background priority, and it prints each directory as it goes so you can see where it has got to. You only need it once; after that the guard watches.
Could it damage my code?
Every original is quarantined before anything is written, so any cut is reversible. The healer only ever removes a payload it can locate exactly, and refuses outright on structured files and UTF-16 rather than guessing. Failing loudly is the design.
Does it phone home?
No. The scanner and the guard make no network requests of their own. The only outbound traffic is git fetch on repositories you asked it to watch, on the hourly ref audit, which you can disable by setting git_interval = 0 in the config. The AI agent talks to the provider you chose, and only while you are using it.
Do I need an AI key?
No. Everything except agent works without one - hunt, repos --repair, the guard, the monitor. Gemini has a free tier, and Ollama needs no key at all because the model runs on your machine. And if you already use Claude Code, Cursor or Codex, polinrider-hunter mcp hands them the same tools with no key of ours involved.
Can the AI agent I already use drive it?
Yes. polinrider-hunter mcp is an MCP server over stdio; register it once (the snippets are in From other agents) and ask your agent in plain words. Anything destructive dry-runs first and needs a second call with confirm: true, so the host has to show you the plan. Or skip MCP and drop the shipped SKILL.md into Claude Code's skills folder; it then runs the CLI itself.
What does the AI provider see?
Your messages and the results of the tools the agent runs - file contents it reads, command output, scan findings. If that must not leave the machine, use ollama or a custom endpoint you host. Keys are stored in config.txt in the state directory, environment variables (ANTHROPIC_API_KEY, OPENAI_API_KEY, …) take precedence, and the tool only ever prints them masked.
Will it rewrite my history without asking?
Never. The guard does not push. repos --repair, the default, does not rewrite anything: it adds one ordinary commit and pushes it as a fast-forward, which fails if anyone pushed in between. repos --fix and repos --excise do rewrite, and push only when you run them, show a dry run first, use --force-with-lease so a push that raced someone else's fails instead of erasing their work, refuse when real work sits on top of the infection, and re-audit the branch afterwards.
Is antivirus enough?
No. Windows Defender detects the older obfuscated variant as Trojan:NPM/PolinRider.DB!MTB, but it did not flag the newer spaced-global.i variant. Signature coverage is not the same as coverage. There is a related trap: a file antivirus has locked cannot be read, and a scanner that treats an unreadable file as a clean one hides the strongest available signal - this one reports it as read-blocked instead.
How do I remove it?
polinrider-hunter uninstall stops the guard and removes the hooks, and prints exactly what it took out. That is reversible - the binary and your state directory stay. polinrider-hunter uninstall --purge goes further: the state directory, the PATH entry and the binary itself. It warns first if the quarantine still holds originals, since deleting those is not recoverable.
Will I know when it finds something?
Yes - a desktop notification, using whatever the platform already provides. Run polinrider-hunter test-notify to confirm they reach you before you need them. If your desktop cannot show one (headless, locked session) it fails quietly rather than refusing to run, and the log still records every detection. Turn them off with notify = false in the config.
Can I see what it is doing?
polinrider-hunter monitor gives a live dashboard - guard health, every watched path, a timeline of detections with the indicators that fired, and the quarantine. Add --web and it prints a http://127.0.0.1:8787 link to open in a browser. It is part of the binary, so it works on any machine that ran the install command: nothing to clone, no Python, no packages. It is read-only and the web view never leaves localhost.
